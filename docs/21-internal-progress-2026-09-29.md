> **과거 학습 기록 — 현재 실행 가이드가 아닙니다.**
> 현재 OAuth2 최소 구성은 [문서 목차](README.md)에서 확인합니다. 이 문서의 금융·ITSM·DB·이전 인증 설정, 주소, 역할 이름과 캡처는 작성 당시의 자료입니다.
> 본문의 “현재”·“최신”도 당시 시점을 뜻합니다. 과거 검사 개수를 이번 검증으로 합산하지 않습니다. 현재 실행 코드는 두 저장소의 `oauth-lab/`이며 USER·ADMIN API 모두 API7을 경유합니다.

# [과거 기록] FinAccess 개발 진행 현황 공유

> **공유일:** 2026.09.29  
> **프로젝트:** 기업 자금관리·이체 승인 모의 시스템  
> **현재 단계:** 이체 요청 → 승인·반려 → 모의 내부 이체까지 구현 및 검증  
> **저장소:** [Greenapple0101/finaccess](https://github.com/Greenapple0101/finaccess)

## 1. 공유 요약

기존 회사·사용자·계좌 모델과 이체 요청 서비스에 HTTP API, 승인·반려, 모의 내부 이체 실행을 연결했습니다.
현재는 이체 요청을 생성하고, 동일 회사의 다른 사용자가 결재한 뒤, 승인된 요청의 출금·입금과 완료 기록을 하나의 트랜잭션으로 처리할 수 있습니다.

이번 추가 개발 후 **전체 127개 테스트가 통과**했으며, 실행 JAR 빌드와 개발용 DB 마이그레이션·애플리케이션 기동을 확인했습니다.
실제 자금이나 외부 은행을 사용하지 않는 로컬 학습용 시스템입니다. 로그인 신원 및 역할 검증은 아직 연결하지 않았습니다.

## 2. 추진 목적

- **금융 업무 이해:** 회사 소속, 계좌 잔액, 이체 요청과 결재 분리, 실패 시 데이터 일관성 구현
- **인증·인가 발표 준비:** Keycloak과 OAuth 2.0/OIDC를 업무 사용자·권한 모델에 연결할 기반 마련
- **Spring 역량 강화:** Controller·Service·Repository 역할, JPA 변경 감지, 트랜잭션, 실제 DB 테스트 학습

단일 Spring MVC·JPA 애플리케이션으로 업무 규칙을 먼저 검증하고 있습니다. Kubernetes·Istio·외부 연동은 후속 확장 범위입니다.

## 4. 이번 추가 개발 내용

### 4.1. 이체 요청 HTTP API

`POST /api/transfers`로 출금 계좌 ID, 입금 계좌 ID, 금액, 요청자 ID를 전달받습니다.

처리 순서는 다음과 같습니다.

1. 필수값·양수 금액·서로 다른 계좌인지 검사
2. 요청자와 출금 계좌의 존재 확인
3. 요청자의 소속 회사와 출금 계좌 소유 회사 비교
4. 입금 계좌의 존재 확인
5. REQUESTED 상태로 저장하고 201 응답 반환

금액은 원 단위 정수이며 소수 입력을 정수로 잘라 받지 않고 거부하도록 설정했습니다.
수취 계좌는 다른 회사 소유도 허용합니다. 요청 생성 시에는 출금하거나 금액을 예약하지 않습니다.

### 4.2. 승인·반려

요청과 같은 출금 회사에 소속된 다른 사용자가 승인 또는 반려할 수 있도록 연결했습니다.

- 요청자 본인의 승인·반려 모두 거부
- 다른 회사 사용자의 결재 거부
- REQUESTED 상태에서만 승인·반려 허용
- 처리자 ID와 처리 시각 저장
- 이미 결재된 요청의 재결재 거부
- 요청 행 잠금으로 동시에 들어온 결재를 직렬화

승인은 실행 허가를 뜻하며, 승인만으로 계좌 잔액이 변경되지는 않습니다.

### 4.3. 모의 내부 이체

승인된 요청에 대해 출금·입금·완료 기록을 하나의 DB 트랜잭션으로 처리합니다.

1. 이체 요청 행을 잠그고 APPROVED 상태인지 확인
2. 실행 사용자 존재 여부 확인
3. 두 계좌를 일정한 UUID 순서로 잠금 조회
4. 실행 사용자가 출금 회사 소속인지 확인
5. 출금 계좌의 잔액 검사 및 차감
6. 입금 계좌의 잔액 증가
7. COMPLETED 상태·실행자·완료 시각 기록
8. 트랜잭션 커밋 후 성공 응답 반환

계좌 잠금 순서를 통일해 반대 방향 이체에서 교착 위험을 줄였습니다.
완료된 요청을 다시 실행하면 409로 거부하며 추가 출금은 발생하지 않습니다.
현재 정책에서는 승인된 요청을 같은 회사 사용자가 실행할 수 있고, 실행자가 요청자와 반드시 달라야 하는 것은 아닙니다.

## 5. API 및 응답 정책

| API | 기능 | 성공 응답 |
| --- | --- | --- |
| POST /api/companies | 회사 등록 | 201 |
| GET /api/companies/{id} | 회사 조회 | 200 |
| POST /api/companies/{companyId}/accounts | 계좌 개설 | 201 |
| POST /api/transfers | 이체 요청 생성 | 201 |
| POST /api/transfers/{id}/approve | 승인 | 200 |
| POST /api/transfers/{id}/reject | 반려 | 200 |
| POST /api/transfers/{id}/execute | 모의 내부 이체 실행 | 200 |

승인·반려·실행 본문에는 `actorId`를 전달합니다. 생성 시 `requesterId`와 함께 현재는 로컬 실습용 입력입니다.

| 응답 | 의미 | 예시 |
| --- | --- | --- |
| 400 | 입력 오류 | 필수값 누락, 잘못된 UUID·JSON, 0원·음수·소수 금액, 동일 계좌 |
| 403 | 업무상 처리 불가 | 다른 회사의 출금 계좌 사용, 자기 결재 |
| 404 | 참조 대상 없음 | 없는 요청·사용자·계좌 |
| 409 | 현재 상태 또는 잔액 충돌 | 미승인 실행, 재결재, 완료 후 재실행, 잔액 부족, 입금 범위 초과 |

업무 예외는 ProblemDetail 응답으로 변환합니다. 예상하지 못한 DB 장애를 입력 오류로 처리하지는 않습니다.

## 6. 상태 및 저장 정보

| 현재 상태 | 허용 행동 | 변경 상태 |
| --- | --- | --- |
| REQUESTED | 다른 사용자의 승인 | APPROVED |
| REQUESTED | 다른 사용자의 반려 | REJECTED |
| APPROVED | 모의 내부 이체 성공 | COMPLETED |

결재 시 결재자·결재 시각, 실행 성공 시 실행자·완료 시각을 추가합니다.
이 정보는 현재 처리 결과를 설명하기 위한 기록이며, 모든 시도와 실패를 보관하는 별도 감사 이벤트 로그는 아닙니다.

## 7. 테스트 및 검증 결과

**검증일: 2026.09.29 / 전체 127개 통과, 실패·오류·건너뜀 0개**

이전 93개에 HTTP·업무 흐름·롤백·동시 처리 검증 34개를 추가했습니다.
JUnit·MockMvc와 Testcontainers의 실제 PostgreSQL을 사용했으며 테스트 DB는 개발용 DB와 분리했습니다.
서비스 트랜잭션 종료 후 별도 조회로 실제 커밋·롤백 결과를 확인했습니다.

| 시나리오 | 확인 결과 |
| --- | --- |
| HTTP 요청 생성 → 승인 → 실행 | COMPLETED 및 양쪽 잔액 반영 |
| 자기 결재·다른 회사 결재 | 403, 기존 상태·결재 정보 유지 |
| 요청·반려 상태의 실행 | 409, 잔액 미변경 |
| 출금 잔액 부족 | 409, 잔액 미변경 및 APPROVED 유지 |
| 출금 SQL 실행 후 입금 오버플로 | 출금까지 롤백, 양쪽 기존 잔액 유지 |
| 완료 기록 저장 실패 | 양쪽 잔액·상태 롤백, 완료 정보 미기록 |
| 완료된 요청 재실행 | 409, 중복 출금 없음 |
| 동시 승인·반려 | 한 건만 성공, 나머지는 상태 충돌 |
| 동일 요청 동시 실행 | 한 번만 이체 반영 |
| 다른 요청의 동일 계좌 동시 출금 | 가용 잔액을 넘는 실행 거부 |
| 반대 방향 동시 이체 | 두 작업 완료 및 최종 잔액 확인 |

완료 저장 실패 테스트는 테스트 DB에 임시 제약을 추가해 실패를 유도한 뒤 제거하는 방식입니다.
운영 코드에 실패 전용 분기를 추가하지 않았습니다.

추가 확인 사항:

- `./gradlew test bootJar` 성공
- 개발용 기존 스키마 V3에서 V4·V5·V6 적용 성공
- 실행 JAR로 local 프로필 기동 및 기본 HTTP 응답 확인

이번 동시 처리 테스트는 정해진 경합 사례의 기본 검증이며, 대규모 부하·장애 환경 검증이나 처리량 측정은 수행하지 않았습니다.

## 8. 설계에서 구분한 책임

| 구성 | 책임 |
| --- | --- |
| Controller | HTTP 입력·응답과 업무 예외 변환 |
| RequestService | 요청 값·참조·회사 소속 검사 후 생성 |
| WorkflowService | 승인·반려·실행의 작업 순서, 트랜잭션·잠금 |
| TransferRequest / TransferStatus | 자기 결재 금지 및 상태 전이 |
| Account | 양수 금액, 잔액 부족, 정수 범위 검사 |
| Repository / PostgreSQL | 저장·조회·행 잠금, 외래키·CHECK 제약 |

트랜잭션은 출금·입금·완료의 원자성을 담당하고, 잠금은 동시 요청이 같은 옛 잔액·상태를 사용하는 문제를 줄입니다.
두 기능이 자동으로 로그인 신원이나 역할을 검증해 주는 것은 아닙니다.

## 9. 현재 제한 및 후속 과제

- **로그인 신원 검증 미연결:** 본문의 requesterId·actorId가 실제 호출자 본인인지 아직 확인하지 않습니다. 현재의 회사 소속 검사는 전달된 사용자 ID를 기준으로 한 업무 검사입니다.
- **역할 기반 인가 미연결:** 담당자·결재자·감사자 역할별 접근 제한은 후속 범위입니다.
- **전체 접근 통제 미완료:** 회사·계좌의 모든 API가 인증·회사별 인가로 보호된 상태는 아닙니다.
- **요청 생성 멱등키 미구현:** 같은 생성 요청을 재전송하면 별도 요청이 생성될 수 있습니다. 완료 요청 재실행 차단과 구분됩니다.
- **감사 로그·원장 미구현:** 현재 결과 기록 외에 전체 시도 이력, 거래 원장, 실패 원인 이력은 후속 과제입니다.
- **잠금 적용 범위:** 현재 내부 이체 서비스 경로를 대상으로 합니다. 다른 쓰기 경로와 임의의 직접 SQL까지 동일하게 통제하지는 않습니다.
- **외부 연동·운영 확장 미진행:** 실제 은행 호출, 외부 응답 불확실성, Kubernetes·Istio, 부하·장애 실험은 아직 적용하지 않았습니다.

다음 우선순위는 Keycloak Realm·Client·사용자·역할 구성과 OAuth 2.0/OIDC 로그인 연동입니다.
검증된 인증 신원을 업무 사용자에 연결한 후, 현재 본문으로 받는 수행자 ID를 신뢰할 수 있는 로그인 정보로 대체하고 역할·회사별 접근 통제를 적용할 계획입니다.
