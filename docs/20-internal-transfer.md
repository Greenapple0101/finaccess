# 20. 모의 내부 이체와 롤백

## 만든 순서

1. V6에 완료 시각·실행자 컬럼을 추가합니다.
2. 계좌 저장소에 잠금 조회를 추가합니다.
3. 엔티티에 complete 행동을 추가합니다.
4. WorkflowService.execute에 출금·입금·완료 순서를 연결합니다.
5. Controller의 POST /api/transfers/{id}/execute와 테스트를 붙입니다.

## 한 요청의 실행 흐름

본문 {"actorId":"사용자 UUID"} → 요청 행 잠금 → APPROVED 확인 → 사용자 조회 →
두 계좌 잠금 → 출금 회사 소속 확인 → 출금 → 입금 → COMPLETED와 실행자·시각 기록 → commit.

요청·반려 상태와 이미 완료된 요청은 실행하지 않습니다. 같은 회사 사용자만 실행할 수 있습니다.
현재 역할 검사는 없고, actorId가 로그인한 본인인지도 아직 인증하지 않습니다.
실행자는 요청자일 수도 있습니다. 자기 결재는 금지하되 승인된 요청의 실행까지 금지하는 정책은 아닙니다.

## 왜 계좌를 잠글까요?

@Transactional만으로 두 요청이 같은 잔액을 읽는 문제를 모두 해결하지는 않습니다.
PESSIMISTIC_WRITE 조회로 트랜잭션 종료까지 쓰기 잠금을 잡습니다.
요청 행을 먼저 잠가 같은 요청의 재실행을 직렬화하고,
두 계좌는 UUID 순서로 잠가 반대 방향 이체도 같은 순서로 계좌를 잠급니다.
잠금 대기 뒤에 현재 잔액을 읽어야 하므로 execute에서는 계좌를 일반 조회한 뒤 잠그지 않습니다.
이 잠금 규칙은 이 실행 경로를 거치는 작업에 적용됩니다. 외부 SQL과 다른 쓰기 경로까지 보장하지 않습니다.

## flush와 commit의 차이

source.withdraw → accounts.flush로 출금 UPDATE를 먼저 DB에 보냅니다.
아직 commit 전이므로 입금 실패 시 이 UPDATE도 롤백됩니다.
학습을 위해 중간 flush를 명시했으며 일반적으로 매 변경마다 flush할 필요는 없습니다.
입금 후 상태를 완료로 바꾸고, 트랜잭션 commit에서 나머지 변경을 반영합니다.
HTTP 성공 응답은 서비스 프록시의 commit이 성공한 뒤 반환됩니다.

잔액 부족과 입금 금액 범위 초과는 409입니다. 실패 후 요청은 APPROVED를 유지하며 완료 정보도 없습니다.
예상하지 못한 DB 장애를 무조건 400/409로 감추지 않습니다.
잔액 부족이 해소되면 승인된 요청을 다시 실행할 수 있습니다.
완료된 요청의 재실행은 409로 거부합니다. 동일 성공 응답을 재현하는 멱등키 기능과는 다릅니다.

## 검증

- HTTP 요청 생성 → 승인 → 실행, 양쪽 잔액과 완료 정보 재조회
- 잔액 부족 시 미변경
- 출금 SQL 실행 후 입금 오버플로: 출금도 롤백
- 완료 저장을 DB 제약으로 실패시킨 경우: 양쪽 잔액과 상태 롤백
- 같은 요청의 동시 실행: 한 번 성공, 나머지 상태 충돌
- 다른 요청의 같은 계좌 출금: 잔액 부족을 넘는 이체 거부
- 반대 방향 이체: 두 작업 완료와 최종 잔액 확인

외부 은행 호출·실제 자금 이동·전체 거래 원장·실행 시도별 감사 이벤트는 아직 구현하지 않았습니다.
