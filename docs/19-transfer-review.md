# [과거 기록] 19. 승인·반려를 연결한 순서

V5 SQL → TransferRequest의 approve/reject → 잠금 조회 → WorkflowService → Controller 순으로 만들었습니다.

POST /api/transfers/{id}/approve 또는 /reject에 {"actorId":"결재자 UUID"}를 보냅니다.
요청 존재 확인 → 요청 행 잠금 → 사용자·출금 회사 확인 → 자기 결재 금지 → 상태 전이 → 처리자·시각 기록 순입니다.
성공 200, 필수값 오류 400, 다른 회사·자기 결재 403, 없는 참조 404, 이미 결재된 상태 409입니다.

엔티티가 상태 전이를 책임지고 서비스는 DB 조회와 회사 소속 검사를 담당합니다.
승인과 반려 모두 요청자 본인이 처리하지 못하도록 정했습니다.
처리자 UUID와 reviewedAt을 함께 저장하며 승인만으로 잔액을 변경하지 않습니다.
PESSIMISTIC_WRITE는 트랜잭션 종료까지 요청 행 잠금을 잡아 동시 결재가 같은 상태를 덮어쓰지 않게 합니다.
모든 변경이 이 서비스를 거칠 때 적용되며 임의의 직접 SQL 수정까지 통제하지는 않습니다.

인증·역할 검사는 아직 없습니다. actorId는 로컬 실습용 입력이며 검증된 로그인 신원으로 교체해야 합니다.
결재자·시각은 최신 결재 결과 기록이지 전체 감사 이벤트 로그는 아닙니다.
